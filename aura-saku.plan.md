### Status: Fixed silent data loss in natural-language recurring "update" (2026-09-30)

Asked directly whether natural-language *update* of a recurring transaction/bill reminder worked (as opposed to the cancel-only feature shipped above). The honest answer at the time was "there's no update tool, so it should just fail or require two messages" — but live-testing against the real Gemini API (via a throwaway `cmd/scratch_update_check`) showed the model was *already* chaining `delete_recurring_transaction` + `create_recurring_transaction` in a single message for phrasing like "ubah netflix jadi 200rb," despite the tool descriptions at the time explicitly telling it never to combine tool calls in one message.

That chaining exposed a real bug, not just a missing feature: `bot.Service`'s dispatch logic only ever inspected `parsedList[0]` for any non-`record` intent, on the documented (and until now correct) assumption that every such intent is singular. With two results back from the model, the second one — the replacement schedule — was silently dropped, so the OLD schedule got canceled with nothing created to replace it. A user saying "ubah netflix jadi 200rb" would have simply lost their Netflix reminder entirely.

Fix: rather than block this pattern, the tool descriptions for `create_recurring_transaction`, `create_bill_reminder`, and `delete_recurring_transaction` (plus the system instruction's blanket "at most one of these per message" rule) now carry an explicit EXCEPTION sanctioning exactly this pairing for updates, so the model's actual behavior and the prompt's stated rules agree instead of conflicting. On the dispatch side, a new `recurringUpdatePair()` helper detects a delete+create pair anywhere in the parsed results and routes to a new `handleRecurringUpdate`, checked *before* the singular-intent fallback — it cancels the old row via the existing `recurring.Service.Cancel`, creates the new one via the existing `recurring.Service.Create` (preserving the "deactivate-then-create" history pattern, never mutating the old row in place), and replies with the new schedule plus a "(previously Rp150.000)" contrast line (`KeyRecurringUpdatedFrom`) when the old amount is known.

Verified: `go build`/`vet`/`test ./...` clean. `TestHandleUpdate_MySubscription_Pro` rewritten to use a fixed timestamp deliberately close to a UTC day boundary (`2026-10-20 23:30 UTC`) instead of `time.Now()` — the original version only caught this bug on the ~1-in-24 runs that happened to straddle real midnight (exactly how it was first found), so the fixed value makes the regression test deterministic on any machine east of UTC instead of flaky.

Chose a genuinely-free-forever stack after independently researching and ruling out several paid/limited alternatives (Supabase Edge Functions alone — no Go runtime, Deno/TS only; Vercel — serverless-only, no persistent process for a Telegram-webhook-driven bot with background schedulers; Fly.io — removed its free tier in late 2024, ~$2/mo minimum with a mandatory card): **Google Cloud's Always Free e2-micro** (1 shared vCPU, 1GB RAM, us-west1 — one of only three regions that qualify) for compute, **Supabase** for managed Postgres, **Upstash** for managed Redis, **Docker Hub** for the image registry, and **Cloudflare Tunnel** for public HTTPS (no static IP needed — Always Free doesn't cover static/reserved IPs, only ephemeral ones).

**Supabase gotcha**: the "Direct connection" host (`db.<ref>.supabase.co`) now resolves **IPv6-only** (Supabase dropped free IPv4 for direct connections), and GCP's default VPC has no IPv6 route at all — `dial tcp ...: connect: network is unreachable`. Fixed by switching to Supabase's **Session Pooler** (`aws-0-<region>.pooler.supabase.com:5432`, username `postgres.<project-ref>`) instead — IPv4-compatible, and still session-mode (not the transaction-mode pooler on 6543), so GORM's prepared-statement caching keeps working exactly as it does against a real direct connection.

**VM build capacity gotcha**: running `docker build` directly on the e2-micro VM exhausted its burst CPU credits mid-compile — the VM became unresponsive to new SSH connections entirely (confirmed via `free -h`/`docker ps -a` after a forced restart: the build process was still consuming what little CPU existed, not actually OOM-killed). Fixed by moving the build off the VM entirely: `scripts/deploy-build-push.sh` cross-builds for `linux/amd64` locally (seconds, vs. minutes-then-crash on the VM) and pushes straight to a private Docker Hub repo; `scripts/deploy-run.sh` runs on the VM and only ever does `docker pull` + `docker run` — never a build. Deliberately **not** `docker-compose.yml`-based in production: that file's `backend` service hardcodes `DB_HOST=postgres`/`REDIS_HOST=redis` for the local bundled-containers dev setup, which would silently override the VM's `.env` Supabase/Upstash values if reused as-is.

Cloudflare Tunnel (`cloudflared` as its own container, `--network host`) gives a public HTTPS URL without an inbound firewall rule or a paid static IP — using the free quick-tunnel mode (`*.trycloudflare.com`), which trades long-term URL stability (it changes on every tunnel restart) for zero setup; a cheap domain + named tunnel is the natural upgrade if/when that becomes a real pain point. Telegram's webhook and Midtrans's Payment notification URL both point at this tunnel URL today — **both need manually updating** if the tunnel is ever restarted and gets a new one, since nothing currently automates that.

One operational gotcha hit during Midtrans sandbox re-testing in production: a **sandbox payment's webhook notification never arrived** — turned out Midtrans's Payment notification URL in their dashboard still pointed at an old pre-migration URL from local testing, not the new tunnel URL (an easy thing to forget to update alongside Telegram's webhook). Diagnosed and recovered by manually replaying a correctly-signed notification directly at the VM's own `localhost:8080` (computing `SHA512(order_id+status_code+gross_amount+ServerKey)` locally so the real server key never left the VM) — a legitimate recovery path specifically *because* `payment.Service.HandleNotification` never trusts the webhook body's own status, only using it to pass signature verification before independently re-querying Midtrans's Core API for the real status (see the Pro-tier subscription Status entry above).

Also added `REDIS_URL` support to `internal/config`/`internal/db` (an existing commit predating this session's visible work, but directly exercised here for the first time against a real managed provider) — `redis.ParseURL`'s `rediss://` scheme auto-configures TLS, which Upstash requires and the separate `REDIS_HOST`/`PORT`/`PASSWORD` fields have no way to express.

### Status: Natural-language subscribe requests bypass the free-tier quota gate (2026-10-01)

Found via live testing: a free-tier user who'd exhausted their daily quota and then typed "mau pro dong" (natural language for "I want Pro") just got the same quota-exceeded message again, with no way forward short of discovering the undocumented `/subscribe` command. Root cause: natural-language intent recognition (`ai.IntentSubscribe`) only happens *after* an AI call, which `bot.Service.enforceQuota` blocks *before* it ever runs — so a quota-exhausted user's subscribe intent was never even seen by the model.

Fixed two ways. First, the quota-exceeded message itself (`KeyQuotaExceededWithReward`/`NoReward`, both languages) now explicitly says to send `/subscribe` instead of a vague "upgrade to Pro" with no actionable command. Second and more substantially, added a lightweight **non-AI** pre-check (`isSubscribeIntentText`, a single regexp) that runs *before* `enforceQuota` and routes straight to `handleSubscribe` on a match — so it works regardless of quota state, at zero extra AI cost. Deliberately does **not** match bare "pro" or "upgrade" alone: this is an expense tracker, and "Pro" is an extremely common product-name fragment ("iPhone 15 Pro", "MacBook Pro") — a bare match would hijack a genuine transaction message like "beli iPhone 15 Pro 20jt" into showing a payment link instead of recording it. Instead requires desire-language adjacent to "pro"/"upgrade" ("mau pro", "pro dong", "upgrade ke pro", or bare "subscribe"/"berlangganan", which don't plausibly appear in a purchase description).

Verified: new `isSubscribeIntentText` unit tests specifically covering the false-positive guard (`"beli iPhone 15 Pro 20jt"` and `"beli macbook pro 25jt"` must NOT be hijacked), plus the positive cases from the real conversation that prompted this. `go build`/`vet`/`test ./...` clean.

### Status: Fixed blank currency and generic description on recurring transactions (2026-10-01)

Found by inspecting the production DB directly: a recurring transaction created from "internet 375000 tiap tanggal 5" (no currency stated) landed with `currency = ''` — `recurring_transactions.currency` is `NOT NULL`, which an empty string satisfies silently, so nothing at the DB layer caught it. Verified: `go build`/`vet`/`test ./...` clean (with `.env` loaded — `make test`'s silent-skip-on-missing-DB-config behavior masked a real assertion failure once already this session; always verify via an isolated `-run` filter when in doubt). ### Status: Daily no-transaction-yet reminder (2026-10-02)

New proactive nudge, explicitly requested: every active user who hasn't recorded a single transaction yet today gets a gentle reminder around 21:00 WIB. First job in this codebase that targets a specific wall-clock time of day rather than just "once per day/month whenever the ticker happens to fire" — every existing scheduled job (`RunBudgetRolloverNudges`, `RunCategoryInsights`, `RunSubscriptionExpiry`) uses a 24-hour `time.Ticker`, which fires at whatever arbitrary time the server process happened to start, not a chosen hour. `RunDailyTransactionReminder` instead ticks every 15 minutes (`dailyReminderInterval`) and is a no-op on every tick outside WIB hour 21 — cheap enough to check on every tick, and the per-user-per-WIB-day Redis idempotency (same `idempotency.MarkSeen` pattern as the rollover nudge) stops it from double-sending across the several ticks that do land inside that hour.

Deliberately uses a fixed WIB (UTC+7) offset rather than per-user timezones — `models.User.TimezoneOffset` exists in the schema but is unused everywhere else in the codebase, and real per-user timezone support is a much bigger feature than this one fixed-time reminder needs for a bot whose primary audience is Indonesian. "Today" is computed by building a UTC `time.Time` from the WIB-shifted date's own Y/M/D components, then subtracting the offset back out — the same documented idempotency and "convert to a concrete UTC range before touching the DB" approach every other `occurred_at` boundary in this codebase uses, avoiding yet another instance of the pgx/timezone footgun found earlier this session.

`RunDailyTransactionReminder` (the actual `scheduler.Job.Run` entry point) is a thin wrapper around the exported `RunDailyTransactionReminderAt(ctx, nowWIB time.Time)`, which does the real work — split out specifically so a test can drive the hour-gate and the WIB-day boundary with a fixed, deterministic instant instead of only passing when run during the real 21:00 WIB hour.

Verified: `go build`/`vet`/`test ./...` clean. New tests: `TestRunDailyTransactionReminder_OutsideTargetHourIsNoOp` (confirms the hour gate), `TestRunDailyTransactionReminder_RemindsOnlyUsersWithNoTransactionToday` (a user with zero transactions today gets reminded, a user who already recorded something doesn't, and a second same-day call never double-sends). Surfaced and fixed a latent micro-flakiness risk in the test helper `newChatID()` (`time.Now().UnixNano()`) while writing these — every prior test in this file only ever needed one chat ID per test, so this is the first to expose that two back-to-back calls can collide on some clock resolutions; fixed locally in this test with a `+1` offset rather than changing the shared helper.

### Status: Multi-account/wallet tracking (2026-10-02)

Closed backlog item 10: money can now be tagged to a specific account/wallet (bank, e-wallet) instead of always landing on a single auto-created "Default" `Account`. Accounts auto-create by name on first mention — the same convention `transaction.resolveCategory` already uses for categories — via a new `account.GetOrCreateByName` (case-insensitive match, original casing preserved for display, unlike a category's internal-only lowercased name). `record_transaction`'s tool schema gained an optional `account_name` field (cascades to `correct_transaction`/`create_recurring_transaction`/`create_bill_reminder` for free, since they all build on the same `transactionProperties()`).

New `/accounts` command lists every account with its own balance plus a total.

### Status: Debt/loan tracking (2026-10-02)

Closed backlog item 11: lending to or borrowing from a specific person is now tracked separately from regular spending ("aku pinjemin Budi 500rb", "aku minjem ke Dania 300rb"). Designed around the real double-entry-accounting answer (asked for explicitly rather than guessed): lending money is an asset conversion, not an expense — cash really leaves the user's account (so their spendable balance does go down), but a matching claim is created so net worth doesn't actually drop, it just changes form from "cash" to "money Budi owes me." This is structurally the same idea as the multi-account transfer above, except the "account on the other end" is a person, not one of the user's own wallets — so it's tracked as its own ledger (new `models.Debt` + `internal/service/debt`, mirroring `internal/service/account`'s shape) rather than folded into `/accounts`/`TotalBalance`.

A loan/repayment is deliberately just ONE plain `Transaction` row (new `TxLoanOut`/`TxLoanIn`/`TxRepaymentIn`/`TxRepaymentOut` types) tagged via a new `DebtID` — unlike a transfer, no linked second leg is needed, since the "other side" is a person with no account balance of their own to move. `Debt.RemainingAmount` is always computed live from its linked transactions' `ConvertedAmount` (never stored), so undoing/correcting a loan or repayment automatically keeps it correct with zero special-case code, and `debt.ListOpen` skips a fully-repaid debt (remaining == 0) the same "computed-away, not deleted" way the account-list fix above does.

Two new tools: `record_loan` (direction `lent`/`borrowed`) and `record_repayment` (direction `received`/`made`, matched against an *existing* open debt — `apperror.ErrDebtNotFound` if there isn't one, never silently fabricated). Excluded from spending reports and budget evaluation entirely by construction, not a new filter: `budget.Service` already sums strictly `type = TxExpense` and `query_spending`'s type enumeration is a fixed list — the new types simply aren't in either, confirmed by a dedicated regression test. New `/debts` command plus natural-language queries (`check_debts`, optionally scoped to one counterparty) list who owes the user and who they owe.

Verified: `go build`/`vet`/`test ./...` clean, including a budget regression test proving borrowing/lending/repaying never moves the Needs/Wants limits or spent totals. Live-verified against the real Gemini API for every phrasing (lend, borrow, repay both directions, both query forms) plus an adversarial check mirroring the move_money fix above — a one-off gift with no loan framing ("aku kasih duit ke Budi 100rb buat jajan") correctly stays a plain transfer, not a misclassified loan.

### Investigated: basic cron/job runner (2026-09-29)

Asked to scope what a basic scheduled-job capability would take, since several backlog items below depend on it and none of them are buildable without it first. (Superseded by the Status entry above — kept here for the reasoning that led to the design.)

**Findings:**
- No scheduler existed at the time — the bot was purely reactive to inbound Telegram webhooks (confirmed by grepping the whole codebase for `cron`/`ticker`/`scheduler`: zero hits).
- Deployment is single-replica (`docker-compose.yml`'s `backend` service, no horizontal scaling config) — an in-process scheduler needs no distributed lock or leader election for now. That assumption breaks the day this ever runs as more than one replica; the fix then is a Postgres advisory lock or a Redis `SET NX` claim per job run, not a rewrite.
- Proactively messaging a user needed no new capability — `messaging.Messenger.SendMessage(ctx, chatID, text)` is already provider-agnostic and used internally by `bot.Service.reply`.

**Design (now implemented as described):**
- New `internal/scheduler` package: a `Runner` holding a list of `Job{Name string, Interval time.Duration, Run func(ctx context.Context) error}`, each on its own `time.Ticker` goroutine, errors logged (never crashing the process), started in `cmd/server/main.go` alongside the Fiber server and stopped via the same signal-driven shutdown context that already exists there.
- No new dependency for v1 — plain stdlib `time.Ticker` covers "every N minutes/hours," which is all the backlog below actually needs. Hold off on a real cron-expression library (e.g. `robfig/cron/v3`) until a feature needs true wall-clock scheduling ("daily at 08:00") that a ticker can't express — even that's a ~10-line "sleep until next 08:00, then tick every 24h" helper, not a new dependency, so this may never be needed at all.
